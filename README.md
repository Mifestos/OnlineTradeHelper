# OnlineTradeHelper

Платформа для автоматизации и оптимизации инвестиционного портфеля на Московской бирже. Система агрегирует исторические котировки, прогнозирует доходность активов с помощью ML-моделей, рассчитывает оптимальные веса портфеля и проводит регулярную ребалансировку по расписанию.

## Зачем и для кого этот проект

Проект задумывался как инструмент для автоматизации рутины частного инвестора. Вместо ручного сбора данных, построения графиков и вычисления весов в Excel, система берет на себя весь цикл: от загрузки свечей до вызова математического оптимизатора и отправки готовой структуры портфеля.

### Как это работает на верхнем уровне:
1. **Сбор данных:** Асинхронный стриминг дневных котировок через T-Invest API (с возможностью переключения на мок-данные для локальной разработки).
2. **ML-пайплайн:** Расчет прогнозной доходности по выбранным тикерам.
3. **Оптимизация:** Передача прогнозов в математическое ядро для расчета весов по Марковицу или Шарпу.
4. **Автоматизация:** Запуск ребалансировки по крону (Celery Beat) и отправка алертов со структурой портфеля в Telegram.

## Архитектура и технические решения

### 1. Модульный ML-пайплайн и расширяемость
Для моделей прогнозирования я заложил единый интерфейс (BaseModel). На данный момент под капотом работают:
* **Prophet** — для выделения долгосрочных трендов и прогнозирования цен.
* **XGBoost** — обучается на наборе технических индикаторов (RSI, momentum, волатильность) с применением регуляризации и клиппинга прогнозов для борьбы с выбросами.
* **Mock** — легковесная заглушка, которая генерирует случайный блуждающий процесс для тестов, чтобы не дергать продакшн-модели.

**Важно с точки зрения архитектуры:** Добавление новой модели изолировано. Достаточно создать класс, унаследовать его от базового и повесить декоратор `@ModelRegistry.register`. API, фоновые воркеры и фронтенд подхватят её автоматически благодаря реестру моделей.

### 2. Математическое ядро и отказоустойчивость (Fallback-механизм)
Оптимизация весов считается через `scipy.optimize`. Доступны две стратегии:
* **Max Sharpe** (максимизация коэффициента Шарпа).
* **Markowitz** (максимизация функции полезности с учетом заданного риска).

**Обработка пограничных кейсов:** Финансовые рынки штормит, и бывают ситуации, когда оптимизатор SciPy не может сойтись (например, если прогнозы по всем акциям оказались хуже безрисковой ставки). Чтобы система в этот момент не падала с ошибкой, я реализовал fallback-режим: веса распределяются пропорционально прогнозам доходностей, а на фронтенд улетает флаг предупреждения, сигнализирующий о нестандартном расчете.

### 3. Управление профилями риска
Параметры оптимизации (выбор модели, бенчмарки, ограничения на максимальную долю одной бумаги в портфеле) сгруппированы в профили:
* **Консервативный:** Prophet + Max Sharpe, жесткое ограничение на позицию до 20%.
* **Сбалансированный:** XGBoost + Max Sharpe, лимит до 35%.
* **Агрессивный:** XGBoost + Markowitz, лимит до 50%.

Также написан CRUD для кастомных профилей: пользователь может закрутить настройки под себя через UI, и они сохранятся в базу.

## Схема взаимодействия компонентов

```text
Frontend (HTML + JS)
       |
       | REST API
       v
FastAPI (oth_api)
       |
+----+----+

|         |
v         v
Celery   Celery
Worker   Beat

|         |
+----+----+
       |
       v
TimescaleDB + Redis
       ^
       |
Streamer (T-Invest API)
```

* **oth_api:** Быстрый асинхронный FastAPI-сервер. Служит фасадом: принимает запросы, валидирует их через Pydantic, бросает задачи в очередь и отдает статус.
* **oth_celery / oth_beat:** Очередь задач на Redis. Beat отвечает за периодические таски (ребалансировка), воркер забирает «тяжелые» вычисления (обучение моделей, SciPy).
* **oth_streamer:** Изолированный сервис для работы с внешним API Мосбиржи. Складывает исторические данные в TimescaleDB.
* **TimescaleDB:** Выбрана как специализированное расширение PostgreSQL для эффективного хранения и быстрого сплита временных рядов (таймсерий котировок).

- **Git / GitHub** — версионирование

### Инструменты разработки

- **VS Code** — IDE

### Архитектурные паттерны

- **Microservices** — разделение на api / worker / beat / streamer
- **Producer-consumer** — Celery + Redis
- **Pub/Sub** — координация через Redis
- **Registry pattern** — реестр ML-моделей (`ModelRegistry`)
- **Factory pattern** — фабрики оптимизаторов и моделей
- **Strategy pattern** — взаимозаменяемые стратегии оптимизации
- **Data classes** — контракт `ModelOutput` для унификации вывода моделей
- **Async/await** — асинхронный I/O в streamer и API
- **Graceful degradation** — fallback-механизм в оптимизаторе

### Методологии и практики

- **REST API** — единый интерфейс для фронтенда
- **Type hints** — статическая типизация Python
- **Dependency Injection** — через FastAPI `Depends`
- **Idempotency** — через `ON CONFLICT DO UPDATE`
- **Health checks** — в Docker Compose
- **Плавное завершение** — `stop_grace_period`, SIGTERM handling
- **Non-root user** — в Dockerfile для безопасности
- **Connection pooling** — asyncpg pool

### Алгоритмы и методы

- **Mean-Variance Optimization** — портфельная теория Марковица
- **Max Sharpe Ratio** — максимизация риск-скорректированной доходности
- **SLSQP** — Sequential Least Squares Programming для задач с ограничениями
- **Covariance matrix estimation** — оценка ковариации доходностей
- **Feature engineering** — RSI, momentum, lagged returns, volatility
- **Regularization** — L1 / L2 для борьбы с переобучением XGBoost
- **Clipping** — ограничение прогнозов для устойчивости
- **Fallback strategies** — пропорциональное распределение при неудаче

## Локальное развертывание

Для запуска проекта в dev-режиме достаточно иметь установленный Docker и Docker Compose. Токен Тинькофф Инвестиций необязателен — без него стример автоматически перейдет в режим симуляции данных.

### 1. Подготовка окружения
```bash
git clone https://github.com
cd OnlineTradeHelper

# Копируем конфиг по умолчанию
cp .env.example .env
```

### 2. Конфигурация (.env)
При необходимости отредактируйте параметры подключения в файле `.env`:

```env
DB_USER=trade_admin
DB_PASSWORD=trade_secure_pass123
DB_HOST=localhost
DB_PORT=5432
DB_NAME=trade_db

REDIS_HOST=localhost
REDIS_PORT=6379

TINKOFF_TOKEN=your_token_here
USE_SANDBOX=true

HISTORY_DAYS=365
DAILY_UPDATE_HOUR=19

TELEGRAM_BOT_TOKEN=your_bot_token
```

### 3. Старт контейнеров

## Инженерные заметки (FAQ для отладки при разработке)

* **Изменения в коде воркера не видны в контейнере:** Из-за агрессивного кэширования слоев Docker при изменении логики внутри `src/services/analytics/` рекомендуется пересобирать контейнер принудительно:
  ```bash
  docker compose build --no-cache celery_worker && docker compose up -d celery_worker
  ```
* **Контейнер базы ушел в циклическую перезагрузку после экстренного выключения:** Если докер-демон упал по OOM или машина выключилась «по грязи» (SIGKILL), TimescaleDB при старте начнет выполнять crash recovery. Это штатный механизм PostgreSQL, нужно просто подождать пару минут, данные не бьются.
* **Обновление зависимостей:** Проект завязан на Poetry. Если правился `pyproject.toml`, обновить lock-файл внутри контейнера можно командой:
  ```bash
  docker compose run --rm celery_worker poetry lock
  ```
* **Откуда берется безрисковая ставка:** Система автоматически парсит SOAP-сервис Центробанка РФ для получения актуальной ключевой ставки. Если сервис ЦБ «лежит» или недоступен из контура, срабатывает хардкод-дефолт на уровень 14%.

## Что планируется сделать в следующих итерациях (Roadmap)

* **Безопасность:** Внедрение полноценного слоя авторизации пользователей (Multi-tenant архитектура) на базе JWT-токенов.
* **Автоторговля:** Реализация модуля `Executor` для автоматического выставления лимитных/рыночных ордеров на биржу по результатам ребалансировки (сейчас система работает в режиме советника).
* **MLOps:** Добавление версионирования и сериализации обученных моделей на диск, чтобы не обучать их с нуля при каждом вызове таски.
* **Математика:** Расширение линейки оптимизаторов (добавление Mean-CVaR модели и факторной ковариации в стиле Barra).
* **Аналитика:** Разработка полноценного модуля бэктестинга стратегий на исторических данных с построением графиков доходности и расчетом максимальной просадки (Maximum Drawdown).
